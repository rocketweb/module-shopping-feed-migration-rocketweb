# Rocket Web Shopping Feed Migration 1.0.0

Released 2026-10-04, alongside Mage-OS Shopping Feed 1.2.1.

## What it does

The optional `rocketweb/module-shopping-feed-migration-rocketweb` package moves reviewed Rocket Web feed configuration into Mage-OS Shopping Feed. Stores without legacy feeds do not need it. Composer installation runs no migration.

An operator previews the source configuration, reviews diagnostics, and explicitly applies an import with its current token and backup reference. The replacement stays disabled. Schedules and upload destinations are held in an encrypted receipt until a separate activation review. Stale/duplicate requests are rejected. Automatic rollback removes only unchanged inactive imports and retains the receipt.

The initial source baseline is base/Google Shopping/Promotions 2.3.4 and Local Inventory 2.3.2, on the same Magento installation and encryption key as the destination. Legacy module code and definitions must remain installed and enabled during setup. Remaining tables alone do not recover inherited defaults.

## Installation and cutover

Install the published companion tag directly from GitHub with Composer. Add its public source repository to the store's root configuration before selecting the stable packages:

```sh
composer config repositories.shopping-feed-migration-rocketweb vcs \
  https://github.com/rocketweb/module-shopping-feed-migration-rocketweb.git
```

Use the [installation instructions](../../README.md#installation) to select the companion's 1.0 line and destination 1.2.1 or later in the 1.x line. The main module's feed management notice links to the optional companion; it neither downloads PHP nor imports data.

Compare actual generated output before activation. Shared global settings, custom PHP, external schedulers, recipient accounts, and fetch URLs need manual review. Destination files use separate subdirectories. Known stock, row-count, URL, identifier, and promotion-column differences are recorded in the earlier acceptance reports.

Before activation, disable the source feed, drain pending work, stop external commands that can restart it, and explicitly approve the current activation preview. Keep the database, code, configuration, output, receipts, and matching encryption-key backup through the rollback period. Edited or activated imports require a reviewed cutover reversal.

## Validation

The [release preparation record](../RELEASE-1.0.0-PREPARATION.md) identifies the verified local source and destination and its repeated unit/database checks. The current importer retains the shipping-weight preservation fix and [published-v1.2.0 generated-output comparison](../ACCEPTANCE-PUBLISHED-1.2.0.md). Previous full installation, browser, transfer, lifecycle, and restore evidence keeps its [Mage-OS 3.5 scope](../ACCEPTANCE-2026-09-30.md) and [Magento 2.4.8 scope](../ACCEPTANCE-2026-10-03.md). Those broader workflows have not all been repeated against 1.2.1. Existing-store and external-recipient acceptance remain cutover gates.

The public CI workflow uses fixture data. Original paid legacy packages are not redistributed or downloaded by CI, so original-XML compatibility and opt-in patch acceptance require a separately supplied local legacy checkout.
